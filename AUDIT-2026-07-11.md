# Codebase Audit — July 11, 2026

Scope: full-stack sweep of `apps/api`, `apps/web`, `packages/core`, `packages/ui`, `packages/db`, and process/config files. Methods: the project's own scan scripts (`check-ledger-gate.sh`, security scan), targeted pattern sweeps (UTC rules, monetary math, DS tokens, banned components, type-safety escapes, silent failures), manual reads of security-sensitive paths (auth, backups, bulk delete, CSV), and a full `pnpm typecheck` (green). Report format follows `.kiro/steering/HARDENING.md`. No code was modified.

Severity within this report is calibrated to this project's own zero-tolerance gates and its single-user LAN threat model — "High" means "violates a gate this project adopted after being burned, on a path that writes to the database."

## High

### H1 — Data Management bulk delete bypasses the transaction lifecycle, leaving balances/holdings/debts corrupt

- **Severity:** High | **Category:** Reliability (data integrity) | **Confidence:** High Confidence (code path read end-to-end; not executed against data)
- **Location:** `apps/api/src/routes/data-management.ts:107-160` (`DELETE /bulk`)
- **Issue:** The route calls `prisma.transaction.deleteMany()` directly (lines 114, 121), bypassing the ledger gate (ADR-013) and therefore every lifecycle hook. Two concrete failure modes:
  1. **`imported-transactions` (line 121):** deletes imported transactions with **no balance adjustment at all**. `Account.balance` is a materialized cache maintained by the balance hook — after this delete it permanently retains the deleted transactions' effects.
  2. **`all-transactions` (line 114):** resets balances to 0 (line 117 — acceptable, since chains build from $0), but never reverses **Holding quantities** (BTC/stock from TRADE transactions), **Debt.currentBalance** (DebtPayment side effects), or **rewards balances**. Investments and debts are left inconsistent with an empty ledger.
- **Impact:** One click in Settings → Data Management silently corrupts account balances (case 1) or investment/debt state (case 2). This is the same class as the hundreds of dollars Prime Visa drift that motivated ADR-013.
- **Reproduction:** Import a CSV → note account balance → Settings → Data Management → check "Transactions (imported)" → Delete → balance is unchanged despite the transactions being gone.
- **Recommended fix:** Either route deletions through `ledgerDelete()` per row (correct, slower), or replicate the _full_ recalculation the approved `transactions.ts` bulk-delete path does — and extend it to holdings/debts (see A1). Then add the file to the ledger-gate approved list with a documented reason (see M5).

### H2 — Bulk-delete balance recalculation writes unrounded floating-point sums to the database

- **Severity:** High | **Category:** Reliability (monetary integrity) | **Confidence:** Confirmed (pattern present; drift magnitude data-dependent)
- **Location:** `apps/api/src/routes/transactions.ts:498-514`
- **Issue:** The post-bulk-delete recalculation accumulates `balance += amt` / `balance -= amt` with no rounding, then writes the raw result to the `balance` Decimal column (line 514). This violates Quality Gate 6 (Monetary Arithmetic — Zero Tolerance). The June 18 remediation added `round2()` to `balance.hook.ts`, `ledger.ts`, `rewards.hook.ts`, `debt-calc.ts`, and `accounts.ts` rebuild endpoints — **this loop was missed**.
- **Impact:** Reintroduces cumulative FP drift (the `-$0.00` / `-0.000010…` class already seen in prod on Cash Wallet) any time bulk delete runs.
- **Recommended fix:** Round each accumulation per the policy: `balance = Math.round((balance + amt) * 100) / 100` (or use `addCurrency` from `@budget-tracker/core`).

## Medium

### M1 — `?key=` query-param auth is accepted on every endpoint, not just downloads

- **Severity:** Medium | **Category:** Security | **Confidence:** Confirmed
- **Location:** `apps/api/src/middleware/auth.ts:22-28`
- **Issue:** The comment says "Allow query-param auth for file download endpoints," but the code applies the fallback to **any** route when the `Authorization` header is absent — including destructive ones (`DELETE /data-management/bulk`).
- **Impact:** The API key leaks into browser history, Caddy access logs, and any intermediary that sees URLs. Anyone who reads a logged URL gets full API access. On a LAN this is bounded, but it's a silent drift from the stated design.
- **Recommended fix:** Gate the query-param branch on the path matching the download route (e.g., `/backups/` + `/download` suffix) before comparing the key.

### M2 — The effective API key is committed to the repo (and the live `.env` uses it)

- **Severity:** Medium | **Category:** Security | **Confidence:** Confirmed
- **Location:** `.env.example:4-5`, `.env.dev:2-3` (both tracked), `apps/web/src/lib/api/request.ts:9`; live root `.env` verified to contain the same default (checked presence only)
- **Issue:** `budget-tracker-dev-key` is the committed default in two tracked files and the hardcoded frontend fallback — and the running environment uses it. The bearer token is therefore a public constant. (Note: `VITE_API_KEY` is baked into the served JS bundle by design, so any device that can load the app can extract whatever key is used — that's inherent to the current architecture and separately documented as accepted auth posture.)
- **Impact:** Bearer auth is effectively decorative: any device on the LAN can call the API with a value published in the git history. This sits a step _below_ the documented "auth 3/10 accepted" posture, which presumed a private token.
- **Recommended fix:** Generate a random key for the live `.env`; empty the placeholder in `.env.example`; decide whether `.env.dev` should be tracked at all. Combined with M1, rotate before fixing M1 loses value.

### M3 — Dashboard income cards still include archived/paused income (known, confirmed still present)

- **Severity:** Medium | **Category:** Reliability | **Confidence:** Confirmed
- **Location:** `apps/api/src/routes/dashboard.ts:154-174`
- **Issue:** The EXPENSE branch guards `archivedAt`/`isPaused` (line 179, added last session); the INCOME branch has no equivalent check, so historical rows from archived/paused income surface on dashboard cards forever (ADR-024 deliberately preserves those rows). This is backlog #1 from the July 10 session — included here for completeness; it has not regressed further.
- **Recommended fix:** Mirror the line-179 guard for `row.income` (`archivedAt != null || isPaused(pausedUntil, today)` → `continue`).

### M4 — Prohibited `as unknown as` casts throughout, including six in the ledger gate itself

- **Severity:** Medium | **Category:** Reliability (type safety) | **Confidence:** Confirmed (locations); impact is latent
- **Location (non-test):**
  - `apps/api/src/lib/lifecycle/ledger.ts:110, 111, 114, 209, 213, 234` — the master write path casts Prisma records to `TransactionRecord`
  - `apps/api/src/routes/investments.ts:253, 351` — metadata casts
  - `apps/web/src/pages/Investments.tsx:123, 387-388`, `apps/web/src/pages/debts/DebtForm.tsx:186-187`, `apps/web/src/components/PayScheduleSettings.tsx:64, 77, 209`, `apps/web/src/pages/settings/DataManagement.tsx:59`
- **Issue:** QUALITY.md: "No `as unknown as` Casts: Prohibited. Use Zod-inferred types instead." These casts silently break on schema drift — the exact failure mode ADR-012 exists to prevent. The concentration in `ledger.ts` is the most concerning: a Prisma schema change that diverges from `TransactionRecord` would type-check clean and fail at runtime in the single most critical write path.
- **Recommended fix:** Unify the Prisma payload type with `TransactionRecord` (derive one from the other, or Zod-parse at the boundary). Frontend instances mostly indicate form-value typing mismatches (`string` vs `Date`) that a corrected form schema would eliminate.

### M5 — The pre-push ledger-gate check is currently red

- **Severity:** Medium | **Category:** Reliability (process) | **Confidence:** Confirmed (script executed)
- **Location:** `bash scripts/check-ledger-gate.sh` fails on: `routes/data-management.ts:114,121` and `scripts/rebuild-balance-chain-backward.ts:121,126`
- **Issue:** Two files use direct `prisma.transaction` mutations without being on the approved list (QUALITY.md table). Per the project's own "Before Git Operations" pipeline, this should be blocking every push right now — meaning the gate is either being skipped or its failures ignored, which erodes the gate.
- **Recommended fix:** `rebuild-balance-chain-backward.ts` writes `balanceBefore`/`balanceAfter` metadata — the same rationale as the `balance.hook.ts` exception — so add it to the approved list (script + QUALITY.md table) with that reason. `data-management.ts` should **not** be whitelisted as-is; fix H1 first, then whitelist with the documented recalculation contract.

## Low

### L1 — UTC-rule violations (letter of the law; behavior likely unaffected)

- **Severity:** Low | **Category:** Reliability | **Confidence:** Confirmed locations; benign-behavior assessment High Confidence
- **Locations & notes:**
  - `packages/core/src/utils/validation.ts:25` — `new Date(year, month, 0).getDate()`: banned local-time constructor + getter in core. Self-consistent (local construct, local get) so days-in-month is correct in any timezone, but it's the exact pattern the preToolUse hook era was meant to eliminate. Fix: `new Date(Date.UTC(year, month, 0)).getUTCDate()`.
  - `apps/api/src/routes/dashboard.ts:371` — `new Date().getFullYear()`: local getter in a route (New Year's Eve edge only).
  - `apps/api/src/lib/pay-periods.ts:21-22` — local getters computing default range bounds.
  - `packages/db/prisma/e2e-seed.ts:222` — local getter in the e2e seed.
- **Excluded as documented exceptions:** `dates.ts` `today()` and its `debt-calc.ts` replica (deliberate local-calendar capture), `backup.ts:24-26` (local-time filenames, decided June 1).

### L2 — CSV exports lack formula-injection neutralization; escape logic duplicated

- **Severity:** Low | **Category:** Security | **Confidence:** Confirmed missing; exploitability low
- **Location:** `packages/core/src/csv/csv-formatter.ts:41-46` and a second independent implementation in `apps/web/src/pages/settings/DataManagement.tsx:21-33`
- **Issue:** Both escape quotes/commas/newlines only. A cell beginning with `=`, `+`, `-`, `@`, tab, or CR executes as a formula when the export is opened in Excel/LibreOffice. Attack chain: a malicious payee/description arrives via an imported bank CSV → user exports → opens in Excel. Realistic likelihood is low (requires poisoned upstream data plus Excel's own confirmation prompts), but this app's whole purpose is round-tripping bank CSVs. The duplication also means the two implementations can drift.
- **Recommended fix:** In the string-cell path only (never numeric cells — negative amounts are legitimate), prefix `'` when the first char is `=+-@\t\r`. Consolidate `DataManagement.tsx`'s local copy onto the core formatter.

- **I2 — Five `@ts-expect-error` directives** in `transactions.ts`, `transactions.linking.ts`, `scheduled-transactions.ts`, each with a justification comment (an upstream `@hono/zod-openapi` inference bug with nullable fields). ## What checked out clean

- **Typecheck:** green across all 11 packages.
- **DB isolation:** `packages/db/.env`, `apps/api/vitest.config.ts`, and Playwright config all point at 5433; root `.env` is gitignored.

- **Frontend responses** are Zod-validated in `request.ts` as designed.

## Requires architectural work or deeper investigation

- **A1 (from H1):** Define what "bulk delete with full integrity" means — per-row `ledgerDelete` (correct, O(n) hook dispatches) vs. a batch recompute contract covering balances **and** holdings, debt balances, and rewards. The existing `transactions.ts` bulk path only recomputes balances, so even the "approved" path is a partial contract worth revisiting.
- **A2 (from M4):** Unify Prisma's generated transaction payload type with `TransactionRecord` so the ledger gate is cast-free.
- **A3 (from L6):** The standing decomposition backlog, headed by `TransactionImportExport.tsx`.
- **A4:** The documented auth upgrade path (sessions, per-device keys) remains the right boundary to revisit at the v0.9 "socialization prep" milestone; M1/M2 are the interim hardening.

## Release recommendation

**Ship with known risks** — for the current single-user, LAN-only deployment. Nothing found is exploitable beyond the LAN, and the two High findings only trigger through Settings → Data Management bulk delete, which should simply not be used until H1/H2 land. For the v0.9/v1.0 socialization milestone, treat **H1, H2, M1, M2** (plus the documented auth upgrade) as do-not-ship blockers.
